# D0.1 — Current Decision Execution Path

Stand: 2026-08-11  
Scope: forensische Bestandsaufnahme, keine Optimierung und keine Produktcode-Änderung

## 1. Ergebnis in einem Satz

Backyrd hat aktuell **nicht einen einzigen Decision-Pfad**:

- Die authentifizierte Mobile-Decision läuft über die deployte Edge Function `decision-v13`, die eine personalisierte SQL-Pipeline (`backyrd_get_decision_spots_v12`) und eine semantische Vector-Pipeline (`backyrd_match_spot_embeddings_v13`) zusammenführt, danach Trust/Distribution anwendet und im Edge Runtime Code fusioniert.
- Die Public-Web-Decision umgeht `decision-v13` vollständig und ruft `backyrd_get_decision_spots_v11` direkt mit deaktiviertem Taste-Weight auf.
- Der Mobile-Debug-Screen ruft separat `backyrd_get_decision_debug_v3` auf und ist nicht der Production-Decision-Pfad.

Die produktiv deployte Edge Function hat im Live-Test folgende Identität zurückgegeben:

```text
model:                backyrd_decision_v13_orchestrator
version:              0.1.10
embedding_model:      text-embedding-3-small
embedding_dimensions: 1536
```

## 2. Evidenzstandard und Grenzen

### Belegt

Diese Analyse stützt sich auf:

1. den aktuell ausgecheckten Commit `8f2583f` auf `main` (identisch mit `origin/main` zum Auditzeitpunkt),
2. den tatsächlichen Call Graph im aktuellen Mobile-, Web-, Edge- und SQL-Code,
3. das Live-PostgREST-OpenAPI-Schema des verknüpften Supabase-Projekts `backyrd`,
4. einen minimalen read-only Live-Aufruf von `decision-v13` ohne User-Personalisierung und ohne Decision-Logging.

Der Live-Aufruf lieferte HTTP 200, `ok: true`, Version `0.1.10`, einen semantischen Kandidaten und keine V12-, Taste- oder Memory-Daten. Der Aufruf diente ausschließlich dem Deployment-Nachweis.

### UNKNOWN

- Ob genau der aktuelle Mobile-JavaScript-Bundle-Commit bereits auf allen installierten Clients aktiv ist, ist ohne Release-/OTA-Telemetrie nicht bewiesen.
- Ob genau der aktuelle Web-Commit öffentlich deployt ist, ist ohne Hosting-Deployment-Metadaten nicht bewiesen.
- Das Live-Schema beweist Existenz und Signaturen der RPCs, aber nicht allein, dass jede Live-Funktionsdefinition byte-identisch mit der kanonischen Migration ist. Für die direkt beobachtete Edge Function ist die Version durch den Live-Response belegt.
- Ein personalisierter Live-Run wurde in D0.1 bewusst nicht mit einem realen User ausgeführt. Dadurch sind konkrete User-Taste-Werte und reale V12-Kandidaten noch nicht Bestandteil dieses Artefakts.

## 3. Echte Entry Points

### 3.1 Mobile Production Entry Point

**Route:** `mobile/app/(tabs)/decision.tsx`  
**Navigation:** sichtbarer Tab `decision` in `mobile/app/(tabs)/_layout.tsx:154-166`  
**Authentifizierung:** Der Tabs-Stack leitet ohne Session auf `/gate`; `runDecision` verlangt zusätzlich `userId` und einen gültigen Access Token.

Damit ist die aktuelle Mobile-User-Decision:

```text

→ mobile/app/(tabs)/decision.tsx
→ Guided oder Free Text State
→ Onboarding Gate
→ get_decision_context_v1
→ Edge Function decision-v13
→ Client Enrichment
→ Client-seitige Top-10-Auswahl

```

### 3.2 Public Web Entry Points

Es gibt zwei öffentliche UI-Einstiege, die denselben Web-Service verwenden:

- Landing Page: `web/app/landing-experience.tsx:180-207`
- Discover Page: `web/app/discover/discover-client.tsx:49-76`

Beide rufen `runWebDecision` aus `web/lib/decision-web-api.ts:106-169` auf.

Der Web-Pfad ist:


## 4. Mobile Input Transformation

### 4.1 State

Der Mobile-Screen hält folgende Decision Inputs lokal:

```text
city
inputMode: guided | free
freeTextQuery
selectedDirections[]
selectedAudiences[]
selectedMoods[]
moodA
moodB
seenSpotIds[]
```

### 4.2 Guided Inputs

Die sichtbaren Optionen sind hart im Client definiert:

- Directions: Essen, Café, Drinks, Kultur, Aktivität, Ausflug
- Audiences: Mit Kind, Date, Freunde, Allein
- Moods: Cozy, Ruhig, Inspirierend, Urban, Chic, Lebhaft

Directions und Audiences erzeugen gemeinsam `preferredPlaceTypes`. Beispiel: `Date` fügt `restaurant`, `bar`, `cafe`, `culture` hinzu. Der Edge Request setzt `strictCategoryIntent: true`, sobald diese Union nicht leer ist.

`buildDecisionV13Query` erzeugt aus Labels und Query Hints einen mehrzeiligen Text. Zusätzlich fügt der Client englische Ranking-Anweisungen hinzu, unter anderem dass Current Intent gegenüber altem Taste bevorzugt werden soll (`mobile/app/(tabs)/decision.tsx:574-627`).

### 4.3 Free Text

Im Free-Text-Modus wird der bereinigte User-Text zur ersten Zeile der Query. City, optionale Directions/Audience/Mood sowie dieselben englischen Priorisierungsanweisungen werden angehängt.

Es gibt auf Client-Seite keine LLM-Normalisierung. `clean` trimmt und kollabiert Whitespace. Negationen und Intent werden erst in `decision-v13` deterministisch per Regex interpretiert.

### 4.4 Mood Mapping ist nicht Ranking-Input des aktuellen Mobile-Pfads

`mapTextToClusterIds` wird im Production-Screen zwar berechnet, aber `mappedMoods.clusterIds` wird nur als UI-Vorschau angezeigt. Der `decision-v13` Request enthält diese IDs nicht. Im V12-Aufruf setzt die Edge Function `p_selected_cluster_ids: null`.

### 4.5 Request Contract an `decision-v13`

Der Mobile Client sendet (`mobile/app/(tabs)/decision.tsx:1396-1415`):

```json
{
  "city": "...",
  "moodA": "... | null",
  "moodB": "... | null",
  "query": "client-constructed multiline query",
  "preferredPlaceTypes": [],
  "audience": [],
  "strictCategoryIntent": true,
  "inputMode": "guided | free",
  "rawFreeText": "... | null",
  "limit": 16,
  "v12Limit": 16,
  "semanticLimit": 24,
  "excludeSpotIds": []
}
```

Bei Remix enthält `excludeSpotIds` die bereits im aktuellen Client-Lauf gezeigten IDs.

## 5. Mobile Production Execution Path

### Stage 0 — User, City und Onboarding

1. `profiles.city` wird als Default City geladen, sofern lokal noch keine City gesetzt ist (`decision.tsx:778-811`).
2. `get_my_taste_profile_status_v1` bestimmt `needs_onboarding`.
3. Bei weniger als fünf `qualified_actions` in `user_taste_profile_v1` wird nach `decision-onboarding` umgeleitet.
4. Das Onboarding liest approved `spots`, akzeptiert 3–8 Spot-IDs und schreibt über `complete_decision_onboarding_v1` den Startgeschmack.

### Stage 1 — Display Context (separat vom V13 Ranking)

Der Client ruft zuerst synchron `get_decision_context_v1(city, moodA, moodB)` auf (`decision.tsx:873-884`).

Diese RPC:

- berechnet Wochentag und Time Bucket in `Europe/Zurich`,
- liest `user_taste_profile_v1.confidence`,
- ruft intern `get_decision_spots_v8` mit Limit 1 auf, um einen Fallback-Modus zu schätzen,
- erzeugt Titel und Body für die UI.

Die RPC liefert **keine Kandidaten an V13**. Ihr Resultat beeinflusst im aktuellen Code primär Display Context/Copy, nicht die V13 Score-Berechnung.

### Stage 2 — Edge Authentication und Intent Detection

`decision-v13`:

1. liest den Bearer Token,
2. erkennt einen authentifizierten User anhand der JWT Claims,
3. normalisiert Strings und Place Types,
4. erkennt Intent deterministisch per Regex,
5. konstruiert `queryText` für das Embedding.

Erkannte Dimensionen im aktuellen Edge Code sind unter anderem Café, warm/cozy, ruhig, romantisch/date, Gespräch, Drinks, Activity, Culture/Art, Solo, Rainy Day, Outing, Kids/Family, Sunday/Weekend, Indoor/Outdoor sowie Ausschlüsse für Restaurant, Party und Bar.

Es gibt in diesem Pfad keinen LLM-Intent-Parser.

### Stage 3 — Context Keys

Vor dem Retrieval ruft die Edge Function auf:

```text
backyrd_get_context_keys_for_decision_v1
→ backyrd_context_keys_from_ml_event_v1
```

Input sind City, Mood A/B und ein JSON Context mit Input Mode, Raw Free Text, Query, Place Types, Audience, Occasions und Category Flags.

### Stage 4 — Query Embedding

Die Edge Function sendet `queryText` an:

```text
POST https://api.openai.com/v1/embeddings
model: text-embedding-3-small
dimensions: 1536
```

Ein Fehler oder eine falsche Embedding-Länge beendet den gesamten Request mit HTTP 500. Für diese Stage existiert im aktuellen Orchestrator kein Retrieval-Fallback ohne OpenAI.

### Stage 5 — Parallele Candidate- und Taste-Aufrufe

Nach Erstellung des Query Embeddings laufen parallel:

```text
1. backyrd_match_spot_embeddings_v13
2. backyrd_get_decision_spots_v12              [nur mit User JWT]
3. backyrd_get_my_place_type_profile_v1         [nur mit User JWT]
4. backyrd_get_my_contextual_taste_v1           [nur mit User JWT]
5. backyrd_get_recent_decision_memory_v1        [nur mit User JWT]
```

Die normale Mobile-UI verlangt einen User Access Token. Deshalb ist ihr erwarteter Modus `personalized_semantic`. Der Modus `semantic_only_no_user_token` ist in der Edge Function vorhanden, wird vom normalen Mobile-Flow aber nicht absichtlich benutzt.

### Stage 5A — Semantic Retrieval

```text
backyrd_match_spot_embeddings_v13
├── backyrd_spot_embeddings_v1.embedding
├── backyrd_spot_ml_documents_v1.document_text/document_json
├── spots
└── categories
```

Eligibility innerhalb dieser RPC:

- `spots.status = approved`
- City match gegen `spots.city` oder ML document JSON city
- Remix exclusions

Ranking ist Cosine Similarity über `<=>`. Es gibt keinen Similarity Threshold; die RPC nimmt die nächsten `semanticLimit` Ergebnisse.

### Stage 5B — Personalized V12 Retrieval

Die Edge Function ruft V12 mit diesen Werten auf:

```text
p_limit          = 16
p_k              = 1.0
p_open_bonus     = 0.0
p_taste_weight   = 0.52
p_explore_weight = 0.055
cluster_ids      = null
```

Der echte SQL-Pfad ist:

```text
backyrd_get_decision_spots_v12
→ backyrd_get_decision_spots_v11
  → backyrd_get_decision_debug_v11
    → backyrd_get_decision_debug_v3
      ├── spots
      ├── mood_token_clusters
      ├── mood_clusters
      ├── mood_tokens
      ├── spot_moods_agg_reviews_v1
      └── spot_is_open_now_safe_v1
    └── backyrd_get_user_taste_affinity_v2
  → distribution_trust_filter_entities_v1
→ spots + categories
→ backyrd_ml_extract_spot_features_v1
→ backyrd_user_feature_weights_v1
→ backyrd_ml_events_v1
→ backyrd_recommendation_runs_v1             [INSERT]
→ backyrd_recommendation_run_items_v1        [INSERT]
```

Wichtig für die Execution-Wahrheit: V12 ist nicht read-only. Jeder authentifizierte V12-Run persistiert einen Recommendation Run und dessen Items, bevor die Edge Function die V12-Liste mit Semantic Candidates fusioniert.

### Stage 6 — Trust/Distribution Eligibility

Nach beiden Retrieval-Listen ruft die Edge Function erneut `distribution_trust_filter_entities_v1` für die Union aller Spot-IDs auf.

Die Live/kanonische Policy lautet für die Decision Surface:

| Effective State | Eligible | Distribution Priority |
|---|---:|---:|
| `normal` | ja | 100 |
| `reduced` | ja | 50 |
| `quarantined` | nein | 10 |
| sonstiger Zustand | nein | 0 |

Quelle sind `safety_content_items` und `distribution_trust_states`.

V11 enthält seit Migration `20260810191712_add_distribution_policy_and_consumption.sql` bereits denselben Trust Filter. Für V12-Personalisierung greift Trust daher innerhalb V11 und nochmals für die kombinierte Liste im Edge Orchestrator. Semantic Candidates erhalten ihn im Edge Orchestrator.

### Stage 7 — Distribution-safe Fallback

Wenn nach Trust Filtering weniger Kandidaten als `limit` vorhanden sind:

```text
distribution_trust_spot_catalog_v1(city, surface = decision)
→ falls weiterhin zu wenig und City gesetzt:
   distribution_trust_spot_catalog_v1(city = null, surface = decision)
```

Diese Fallback-Spots werden der Semantic-Liste mit `similarity = 0` und dem Dokumenttext `Distribution-safe alternative candidate` hinzugefügt. Der zweite Schritt kann bewusst Spots außerhalb der angefragten City liefern.

### Stage 8 — Metadata und Fusion

Die Edge Function lädt für alle verbleibenden IDs per Service Role:

```text
spots(id, name, city, category_id, categories(name))
```

Anschließend dedupliziert sie nach `spot_id`, berechnet Score-Komponenten, sortiert und diversifiziert.

Die V13-Fusionsformel im aktuellen Code ist:

```text
combined_score =
    normalized_v12_score * personalized_weight
  + normalized_semantic_similarity * semantic_weight
  + source_bonus
  + intent_boost
  + category_fit_component
  + category_mismatch_penalty
  + place_type_boost
  + contextual_taste_component
  + recent_memory_component
  + v12_only_penalty
  + weak_intent_penalty
```

Die Gewichte hängen von `categoryOnlyMode`, explicit Category Intent und strong Culture Intent ab. Die endgültige Sortierung ist:

```text
1. distribution_priority DESC
2. combined_score DESC
3. bester V12/Semantic Source Rank ASC
```

Danach dedupliziert `diversifyCandidates` normalisierte Namen und begrenzt im Family-Modus die frühe Culture-Dominanz.

### Stage 9 — Client Top 10 und Enrichment

Der Edge Orchestrator liefert maximal 16 Kandidaten. Der Client:

1. mappt V13 Candidate-Felder in den UI-Typ,
2. entfernt bei Remix bereits gesehene IDs,
3. nimmt maximal zehn IDs,
4. lädt parallel `spots`, `spot_photos`, `reviews`, `spot_effective_content_v1` und `spot_hours`,
5. lädt danach `categories`, falls Category IDs vorhanden sind.

Diese Enrichment-Daten verändern die bereits festgelegte V13-Reihenfolge nicht. Sie dienen Photos, Beschreibung, Keywords, Review Snippets, Öffnungszeiten-Text und UI Copy.

### Stage 10 — Explanation und UI Copy

Der aktuelle Mobile-Run ruft `decision-copy` **nicht** auf.

Obwohl `loadDecisionCopy` weiterhin im Screen definiert ist, existiert kein Call Site. Stattdessen baut `buildV13Copy` deterministisch aus `human_reason`, `why_this`, Category und City die Anzeige-Texte. Die Edge Function erzeugt `human_reason` aus Intent, Candidate Document Preview, Source Membership und Place-Type-Profil.

### Stage 11 — Persistence und Outcome Logging

Nach erfolgreichem Enrichment:

```text
create_decision_session_v1
→ decision_sessions

log_decision_impressions_v1
→ decision_impressions

pro Spot: backyrd_ml_log_event_v1(decision_impression)
→ backyrd_ml_events_v1
→ ggf. kontextuelle Lernfunktionen (nach Event-Typ und Signalstärke)
```

Like/Dislike/Open schreiben zusätzlich:

```text
log_decision_action_v1
→ backyrd_log_decision_action_v1
→ decision_actions

backyrd_log_taste_event_v3
→ user_taste_events_v2 (Compatibility Event; Fehler werden verschluckt)

backyrd_ml_log_event_v1
→ backyrd_ml_events_v1 und aktuelle ML-Lernpipeline
```

Alle `backyrd_ml_log_event_v1` Calls im Mobile Client sind durch Consent `personalized_recommendations` gegated. Session/Impression-Persistenz ist davon getrennt.

## 11. D0.1 Unknowns für den nächsten Forensics-Schritt

1. Byte-identische Live-SQL-Definitionen gegenüber dem lokalen kanonischen Migrationstext sind noch nicht per `pg_get_functiondef` aus Production exportiert.
2. Ein authentifizierter Live-Trace mit realem User-Taste-State fehlt noch.
3. Candidate Counts und konkrete Ausschlüsse für drei reale Decision Runs fehlen noch; das ist Teil des späteren End-to-End Execution Trace Deliverables.
4. Die genaue aktuelle Coverage/Staleness aller Spot Embeddings ist noch nicht gemessen.
5. Release-/OTA- und Web-Deployment-Metadaten fehlen, um Client-Commit und öffentlich deployten Commit zweifelsfrei gleichzusetzen.
6. D0.1 klassifiziert existierende Pfade, bewertet aber noch nicht ihre Recommendation-Qualität, Performance oder Fehlerhäufigkeit.

## 12. D0.1 Abschluss

Die fünf Startfragen sind für den aktuellen Repository- und Live-Backend-Stand beantwortet:

1. **Welche Datei startet eine User Decision?**  
   Mobile: `mobile/app/(tabs)/decision.tsx`; Public Web: zwei UIs über `web/lib/decision-web-api.ts`.

2. **Welche Functions/RPCs/Edge Functions werden tatsächlich aufgerufen?**  
   Der vollständige Mobile- und Web-Call-Graph ist oben dokumentiert und die direkten Mobile-RPC-Signaturen sind live verifiziert.

3. **Was ist Production, Fallback, Debug oder Legacy?**  
   Die Klassifikation steht in der Version Inventory. Besonders wichtig: V13 Mobile, V11 Public Web, Debug V3 separat.

4. **Welche Datenbankobjekte hängen daran?**  
   Direkte und indirekte Objekte sind im Dependency Graph und Live-Inventar aufgeführt.

5. **Welche externen Modelle/APIs sind Teil der Pipeline?**  
   Im aktiven Mobile Ranking ist OpenAI `text-embedding-3-small` der einzige externe AI-Model-Call. Copy und Intent sind im aktuellen Request deterministisch.
