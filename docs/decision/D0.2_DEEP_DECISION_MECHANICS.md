## 1. Executive Summary

Current Mobile Decision is a two-retriever hybrid. V12 retrieves and reranks a personalized SQL list; V13 semantic retrieval independently retrieves nearest Spot embeddings. The Edge Function filters the union through Distribution, adds approved fallback inventory if needed, calculates a deterministic additive fusion score, orders it, diversifies normalized duplicate names, and returns up to 16 candidates. Mobile takes at most ten, enriches them, displays them, and persists a separate Decision session.

The exact result is dominated by four layers:

1. product and Distribution eligibility;
2. explicit category/intent fit and mismatch terms;
3. semantic similarity and normalized V12 score;
4. contextual Taste and recent-memory adjustments where data exists.

V12 itself is materially affected by review-Mood volume, two independent Taste systems, direct Mood-feature matches, recent ML events, random exploration, and a category-position penalty. The V12 recommendation run is written before V13 fusion and is not a record of what Mobile displayed.

Three rolled-back synthetic traces were executed against a fresh canonical database. The actual `detectIntent`, `buildQueryText`, and `fuseCandidates` functions were loaded from the current Edge source and executed without reimplementing their mechanics. Every #1/#2 score delta reconciles exactly.

No new P0 was found. A P1 Distribution defect was found: the semantic-only constructor omits `distribution_priority`, so the documented priority ordering is not enforced for semantic-only/fallback candidates. Quarantined and excluded candidates are still removed before fusion; the defect affects the ordering of eligible `REDUCED` versus `NORMAL` candidates.

## 3. Exact Ranking Architecture

The active Mobile formula begins after the path documented in D0.1:

```text
approved V12 candidates                 approved semantic candidates
          │                                      │
          └────────────── union by Spot ID ──────┘
                              │
                    Distribution eligibility
                              │
                   approved fallback if short
                              │
                    metadata + V13 fusion
                              │
                  Distribution/score/source sort
                              │
                  normalized-name diversity
                              │
                       Edge maximum 16
                              │
                   Client Remix exclusion
                              │
                       Client maximum 10
```

Product eligibility is a hard precondition. Distribution is a separate eligibility/exposure layer. Score cannot make a non-approved, quarantined, or excluded Spot eligible.

## 4. Low-level SQL scoring: V3 and V11

### 4.1 V3

For Spot `s`, selected Mood clusters `C`, query `q`, scale `k`, and open bonus `b`:

```text
raw_mood(s) = Σ review_mood_count(s, cluster), over C
              or over every valid review Mood when C is NULL

mood_norm(s) = 1 - exp(-raw_mood(s) / k)

text(s,q) = 1.0  if normalized Spot name contains the complete normalized q
          = 0.5  else if normalized city contains the complete normalized q
          = 0.0  otherwise

open(s) = b if spot_is_open_now_safe_v1(s) is true, else 0

V3(s) = mood_norm(s) + 0.15 × text(s,q) + open(s)
```

| Component | Input/default/missing behavior | Raw/normalized range | Eligibility/order effect |
|---|---|---:|---|
| Product state | `spots.status`; only approved | Boolean hard gate | eligibility |
| City | `spots.city`; null/blank means all cities | Boolean hard gate | eligibility |
| Raw Mood | `spot_moods_agg_reviews_v1`; missing = 0; negative unavailable | integer `[0,∞)` | ordering |
| Mood normalization | `k`; Mobile uses `1`; nonnegative | `[0,1)` | ordering |
| Text | complete query substring, not token relevance | `{0,.5,1}` | ordering |
| Open now | safe helper; missing/error = false | `{0,b}` | ordering only; Mobile `b=0` |

V3 orders by `final_score DESC`, then raw Mood strength, then name. With Mobile's `p_selected_cluster_ids = NULL`, the base Mood score counts all review-Mood rows, not the user's current Mood. This is a material, query-independent review-volume signal.

### 4.2 V11

V11 takes V3 candidates, legacy concept affinity, and deterministic exploration:

```text
tw = clamp(p_taste_weight, 0, .35)
ew = clamp(p_explore_weight, 0, .20)

affinity(s,u) = Σ user_taste_concepts_v2.weight × Spot concept strength
taste11(s,u) = sigmoid(2 × affinity) = 1 / (1 + exp(-2 × affinity))
explore11(s,u) = deterministic hash(user, Spot, current date) / 1000

V11(s) = (1 - tw - ew) × V3(s)
         + tw × taste11(s,u)
         + ew × explore11(s,u)
```

Missing affinity becomes `0`, therefore missing legacy Taste becomes `sigmoid(0) = .5`, not zero. `taste11` is `(0,1)`, exploration is `[0,.999]`, and Mobile-through-V12 uses `tw=.10`, `ew=.055`. V11 requests at least ten base candidates.

The current V11 wrapper applies Distribution eligibility and nominally orders `distribution_priority DESC`, score descending, then inherited order. A normal candidate has priority 100 and a reduced candidate 50, so within V11 a reduced candidate cannot outrank a normal candidate.

## 5. V12: what it adds

V12 requires `auth.uid()`. It clamps output limit to 1–20 and retrieves:

```text
candidate_limit = max(12, min(p_limit × 5, 40))
```

Mobile requests 16, therefore V12 asks V11 for 40 and returns at most 16. Before scoring, it inserts a recommendation run declaring `candidate_count=40` and `shown_count=16`; these are configured limits, not observed counts.

### 5.2 Exact V12 score

The query terms are only Mood A, Mood B, and hard-coded cozy/romantic expansions. Arbitrary free-text words do not enter V12 Mood relevance.

```text
taste12(s,u) = Σ spot_feature_strength
                   × user_feature_weight
                   × max(.25, confidence)

mood_relevance(s) = min(2,
  Σ distinct matched mood/mood_concept/keyword feature strength)

direct_mood = .30 if relevance ≥ 1.15
            = .22 if relevance ≥ .70
            = .10 if relevance ≥ .35
            = 0 otherwise

mood_penalty = (-.18 if relevance ≤ .05 and V11 base < .42 else 0)
             + (-.22 if category is Nachtleben/Club, request is cozy/romantic,
                       and relevance < .9 else 0)
             + (-.10 if category is Bar, request is cozy/romantic,
                       and relevance < .7 else 0)

behavior = (-.07 if impression within 3 days)
         + (-.30 if dislike within 21 days)
         + (+.16 if like/open/favorite_add within 45 days)

explore12 = random() in [0,1)
category_position = row_number within category by V11 base, Taste, name
diversity_penalty = 0 for position 1, else -.07 × (position - 1)

V12(s) = .55 × V11(s)
       + p_taste_weight × taste12(s,u)
       + direct_mood
       + mood_penalty
       + min(p_explore_weight,.08) × explore12
       + behavior
       + diversity_penalty
```

Mobile uses `p_taste_weight=.52` and `p_explore_weight=.055`. `taste12`, behavior sums, and category penalty have no aggregate score cap. Negative V12 scores are allowed. V12 orders score descending and name ascending. It inserts one run item for each returned V12 row with the pre-fusion score and components.

V12 therefore reranks meaningfully. In Trace 2, strong historical Café/quiet weights moved Hearth Café to V12 rank 1 despite a current Bar request; V13 category/intent fusion subsequently put Bars first.

## 6. Semantic score

### 6.1 Query and embedding

`buildQueryText` concatenates free/guided query, city, Mood A/B, preferred/excluded place types, audience, occasions, and an English instruction that current intent should precede old Taste. The Edge Function requests:

```text
model = text-embedding-3-small
dimensions = 1536
```

An embedding HTTP error or non-1536 result fails the whole Edge request. There is no non-embedding retrieval fallback.

### 6.2 Spot document and similarity

`backyrd_match_spot_embeddings_v13` joins embedding, ML document, Spot, and category; requires approved state; applies city and Remix exclusions; and returns nearest cosine neighbors without a threshold.

```text
semantic_similarity = 1 - cosine_distance(query_embedding, Spot_embedding)
semantic_norm = clamp((semantic_similarity - .50) / .25, 0, 1)
```

Theoretical raw range is `[-1,1]`. Normalization makes every similarity `≤.50` worth zero and every similarity `≥.75` worth one. Controlled trace ranges were `.2665–.9985`; saturation occurred frequently. Candidate limit is clamped to 1–100; Mobile requests 24.

Missing embeddings are absent from semantic retrieval but may still enter through V12 or fallback. A persisted embedding is stale when its `source_hash` or `document_version` differs from its persisted document. Pending/processing embedding jobs represent a further source-to-document freshness signal.

## 7. Exact V13 fusion

### 7.1 Mode weights

| Mode, evaluated in this order | Personalized | Semantic | Overlap bonus |
|---|---:|---:|---:|
| `categoryOnlyMode` | `.12` | `.46` | `.044` |
| explicit place-type intent | `.18` | `.44` | `.044` |
| strong Culture intent without earlier match | `.32` | `.50` | `.08` |
| default | `.48` | `.42` | `.08` |

The overlap bonus is `.08` when both sources contain the Spot and zero otherwise; explicit category intent multiplies it by `.55`.

### 7.2 Complete additive equation

```text
V13(s) = clamp(V12(s),0,1) × personalized_weight
       + semantic_norm(s) × semantic_weight
       + overlap_bonus
       + intent_boost
       + category_fit
       + category_mismatch
       + place_type_profile
       + contextual_taste
       + recent_memory
       + v12_only_penalty
       + weak_intent_penalty
```

| Term | Exact bounds and conditions |
|---|---|
| Personalized | `[0,.48]`; negative V12 becomes 0, V12 above 1 saturates |
| Semantic | `[0,.50]`; often saturated once raw cosine similarity reaches `.75` |
| Intent | sum of rules below, final clamp `[-.55,.58]` |
| Category fit | additive rules below, clamp `[0,.50]` |
| Category mismatch | additive rules below, clamp `[-.65,0]` |
| Place-type profile | explicit max `±.07`, otherwise `±.18`; strong Culture multiplies by `.45` |
| Contextual Taste | category-only `±.18`, explicit `±.22`, otherwise `±.30` |
| Recent memory | `[-.56,.08]` |
| V12-only | `-.035` for raw V12 ≥ `.8`, `-.09` for ≥ `.6`, else `-.13` |
| Weak intent | nightlife/talk and weak cozy-Café V12-only rules, floor `-.22` |

### 7.5 Profile, contextual Taste, and memory

Place-type profile:

```text
contextual = clamp(context_weight × .09, ±(.06 explicit else .16))
             × clamp(context_confidence × 3.2, .35, 1)
global     = clamp(global_weight × .045, ±(.025 explicit else .08))
             × clamp(global_confidence × 2.2, .20, 1)
profile    = clamp(contextual + global, ±(.07 explicit else .18))
```

Contextual Taste matches category, price text, city, or document/searchable text:

```text
Σ weight × clamp(confidence × 7.5, .15, 1) × scope_multiplier
scope multipliers: category_situation .72, situation .50, category .34, global .14
```

Recent memory uses the latest 48-hour event per Spot. The RPC supplies penalty/bonus, then Edge adds another repetition penalty. Resulting common values are approximately: dislike `-.40` default/`-.44` category-only; positive `-.07`/`-.12`; open `-.035`/`-.06`; seen `-.075`/`-.10`.

## 8. Ordering and diversity

Intended order is:

```text
distribution_priority DESC
combined_score DESC
min(V12 rank, semantic rank) ASC
```

Spot IDs are deduplicated by a `Map`; V12 insertion wins the base object and semantic data is merged. Equal remaining comparisons return zero; JavaScript stable sort preserves insertion order. V12's `random()` means repeated authenticated runs are not globally deterministic even when all input state is unchanged.

`diversifyCandidates` then removes normalized-name duplicates. In family mode, at most three Culture candidates are accepted in the first pass; a second pass fills remaining slots without violating name dedupe.

Confirmed exception: semantic-only candidates never receive the required `distribution_priority` property in their constructor. The comparator evaluates `undefined` differences as `NaN`, effectively treating those comparisons as ties. In Trace 3 a reduced Cellar Bar (priority map 50) stayed ahead of a normal Night Owl Club because their semantic-only scores were `0` and `-.08`. Thus a reduced candidate can outrank normal in semantic-only/fallback space. This is D0-F-002 (P1), not a P0 because non-eligible states are removed before fusion.

## 14. Actual learning chains

Default ML strengths are: impression `.01`, like `.22`, dislike `-.10`, open `.14`, Remix `-.025`, favorite add `.38`, remove `-.18`, review create `.48`, update `.20`, detail `.08`, search click `.10`, map tap `.08`.

`backyrd_ml_log_event_v1` always inserts the supported event, but updates feature weights only when a Spot exists, absolute strength is at least `.05`, and type is like/dislike/open/favorite/review/detail/search/map. Impression and Remix therefore persist but do not update long-term feature weights. Triggers separately update contextual Taste and place-type profile under their own learnable-event rules.

| User action | Proven chain | Future rank effect |
|---|---|---|
| impression | Mobile ML RPC → ML event | V12 `-.07` for 3d; recent-seen memory for 48h; no long-term weights |
| open | ML event + Decision action `tapped` + compatibility Taste event | positive feature/context/place-type learning; V12 `+.16` for 45d; short-term repeat penalty |
| like | ML event + action `exact_mood` + compatibility event | positive feature/context/place-type learning; V12 `+.16`; short-term repeat penalty |
| dislike | ML event + action `not_there` + compatibility event | damped negative feature/context/place-type learning; V12 `-.30`; strong short-term penalty |
| Remix | ML event with no Spot, linked to the previous Decision ID because state is cleared afterwards | no feature learning; analytics only for future rank |
| save/favorite | favorites table is observable; ML event types exist | current product call site logging `favorite_add/remove` was not found, so no proven Decision learning chain |
| was-here | legacy action type and downstream review candidate logic exist | no active Decision-screen call site found; no current ML event type |
| review/Moment | review can explicitly/automatically link to Decision; review content updates Spot document asynchronously | current review UI does not call `review_create/update` ML event; social Moment itself is ignored |

Negative learning is deliberately damped. For negative events, Mood/concept deltas multiply by `.62`, category/keyword by `.78`, price by `.45`, and negative city is ignored. If the rejected feature matches the explicitly requested Mood, it receives another `.22` multiplier. Negative weights survive in global, contextual, and place-type tables; they are not merely session state.

## 15. Short-term versus long-term preference

The engine distinguishes four layers:

1. long-term legacy concepts in V11;
2. long-term feature weights in V12;
3. context/place-type preferences in V13;
4. exact-Spot recent memory in V12 windows and V13's 48-hour memory.

Current-session intent is not learned state. It is the query, deterministic intent flags, semantic embedding, and explicit category terms. Conflict resolution is additive, not a hard override. Explicit category mode reduces personalized V12 power to `.18`, semantic to `.44`, adds category/intent terms up to roughly `+1.08`, and caps contextual Taste at `.22`; this usually lets current category intent win.

Trace 2 proves the mechanism. Historical Taste strongly favored Café/quiet and disliked Bar/lively. Hearth Café became V12 #1, but the final Top 2 were Bars because explicit Bar fit/intent outweighed the old profile. Historical dislike still reduced each Bar by place-type `-.06525` and contextual Taste `-.22`.

## 17. Negation behavior

Deterministic recognition is phrase-list based:

| Input | Deterministic result |
|---|---|
| `keine Bar`, `kein Bar`, `nicht Bar`, `ohne Bar`, `keine Drinks`, `kein Alkohol` | excludes Bar / `avoidBars` |
| `kein Restaurant`, `nicht Restaurant`, `ohne Restaurant`, `kein Essen`, `nicht Essen` | excludes Restaurant / `avoidRestaurant` |
| `kein Club`, `keine Party`, `nicht Nachtleben` | excludes nightlife / `avoidParty` |
| `nicht laut`, `nicht zu laut` | wants quiet; also avoids party; conversation for `nicht zu laut` |
| `nicht teuer` | no deterministic price constraint |
| `nichts schickes` | not understood as negation; `chic` can still count as Mood signal |
| `nicht touristisch` | no deterministic behavior |

Unrecognized negative text still enters the embedding, so it may have semantic influence, but there is no deterministic guarantee that the embedding respects logical negation.

## 22. Persistence Truth

V12 persistence and displayed Decision persistence are separate systems:

| Store | What it represents | What it does not represent |
|---|---|---|
| recommendation run | V12 request parameters and configured limits | V13 union, semantic-only, fallback, final display |
| recommendation run items | returned V12 rank/score/components before fusion | V13 score/rank or client Top 10 |
| Decision session | user, city, Mood A/B created after client enrichment | query, model/version, V12 run ID |
| Decision impressions | exact persisted client Spot IDs, ranks, and display `why` | combined score/source components |
| ML impression events | consented per-Spot engine/query/source/score context | guaranteed completeness when consent/offline call fails |

There is no reliable key joining a V12 recommendation run to a Decision session. Semantic-only and fallback candidates never appear in V12 run items. In the traces, runs declared `40/16` candidates/shown while actual items were `10`, `10`, and `2`. Remix invokes V12 again, creating another recommendation run, and later creates another Decision session.

The actual initial displayed Top 10 can be reconstructed from Decision impressions if session/impression persistence succeeded. Full ranking mechanics can only be reconstructed when the asynchronous consented ML event context also succeeded. Historical V12 recommendation runs alone cannot reconstruct what the user saw.

## 25. Explainability Truth

V3 creates `why_this` from Mood/text/open cases. V12 may append a sentence for Taste, Mood relevance, or a strong negative behavior adjustment. V13 creates `human_reason` from deterministic intent and substring checks over category, ML document preview, matched tokens, and terms. Mobile `buildV13Copy` chooses these fields and category/city templates; `decision-copy` is not called.

The Edge explanation JSON accurately records additive V13 components for candidates that have them. Human copy is not a faithful attribution model:

- it can emphasize a document substring that contributed only indirectly through semantic similarity;
- it can omit category mismatch, recent-memory, Distribution, and saturated V12 contributions;
- V12 `why_this` does not know V13 semantic/category fusion;
- a high semantic score is not decomposed into which document phrase caused similarity;
- fallback text can still produce heuristic copy despite semantic similarity zero.

Trace 2's actual Bar ranking was driven by category/intent and V12 saturation while the historical Bar dislike subtracted `.28525`; human copy does not necessarily reveal that conflict. Explanation is therefore directionally useful but not a complete causal statement.

## 32. Latent ground truth

Observed Backyrd data and latent synthetic truth must be separate:

```text
latent User × latent Spot × latent Moment fit
                 │
       generates noisy reviews/actions/content
                 │
       current engine sees observed data only
                 │
evaluation compares ranked/displayed Spots with latent utility
```

Required latent dimensions derive from current product questions: user affinity for category/Mood/price/noise/activity style; current occasion/audience fit; distance/time/open/availability fit; novelty tolerance; social-context fit; Spot's true atmosphere/price/quality; and satisfaction/visit probability. The simulator must not expose these values to the engine. Otherwise it would reward the engine for reproducing its own generated observations.

## 33. Anti-overfitting split recommendation

- **Development scenarios:** visible seeds, latent rules, and detailed traces; Decision engineers may inspect and iterate.
- **Regression scenarios:** fixed observed fixtures and expected mechanics; engineers may inspect inputs/expected outputs but changes require explicit baseline review.
- **Locked holdout scenarios:** hidden seeds, latent truth, noise realizations, and outcome labels; engineers see only aggregate predeclared metrics after submission.

The engineer may inspect engine-visible observed data in all splits. They must never inspect holdout latent User/Spot/Moment variables, individual holdout satisfaction labels, or generation seeds. Split assignment should be by User, Spot archetype, and scenario family—not just random events—to prevent leakage.

## WHAT BACKYRD DECISION IS TODAY

A hybrid approved-only, Distribution-filtered recommender combining a personalized SQL ranker (V12) with embedding retrieval and deterministic V13 intent/category fusion, followed by name diversity and a client Top 10.

## WHAT ACTUALLY DETERMINES A RESULT

Eligibility first; then explicit category/intent fit, saturated semantic similarity, normalized V12 score, contextual Taste and recent memory. Review-Mood volume and learned feature Taste materially shape V12. Distribution priority is intended to precede score but is missing on semantic-only candidates.

## WHAT BACKYRD KNOWS ABOUT THE USER

Profile city, onboarding state, legacy concepts, learned feature weights, place-type/context profiles, recent consented Decision events, and exact-Spot memory. It does not know latent satisfaction or automatically treat every save/review as learning.

## WHAT BACKYRD KNOWS ABOUT THE SPOT

Approval, city/category/price/location/content, Moods/concepts, selected intelligence/taxonomy, hours, reviews, ML document/embedding, and Distribution state. Data coverage varies sharply even though Basel embedding coverage is complete.

## WHAT BACKYRD KNOWS ABOUT THE MOMENT

The submitted city, query, guided types, audience, occasions, Moods, input mode, and deterministic flags for family/date/solo, Sunday/weekend, indoor/rain, conversation, culture/activity/nightlife and a small set of exclusions.

## WHAT BACKYRD CURRENTLY DOES NOT KNOW

Actual weather, distance from the user, live opening/availability/capacity, transaction completion, real visit, and true satisfaction. It does not deterministically understand general natural-language negation or price constraints.

## WHERE DECISION QUALITY CAN CURRENTLY FAIL

Semantic-only Distribution ordering, closed/far/unavailable recommendations, sparse observational data, review-volume-driven V11 base, semantic saturation, random V12 ties, cross-city fallback, unrecognized negation, pre-fusion persistence, incomplete learning wiring, and heuristic explanation are proven failure classes.

## WHAT WE CAN MEASURE TODAY

Candidate sources, eligibility, every V12/V13 score component, final persisted client impressions, opens/likes/dislikes, some Decision-linked reviews, coverage, embedding freshness, and controlled component latency.

## WHAT WE CANNOT YET MEASURE

Reliable reservation/navigation completion, real visits, satisfaction, causal long-term quality, or a complete historical Top 10 with all score components when consented event logging was absent.

## WHAT D1 MUST SIMULATE

Observed Users, Taste/context/memory, Spots/features/documents/embeddings, candidate generation, eligibility, Distribution, exact ranking/fusion/diversity, split persistence, events, learning, partial observability, and separately hidden User×Spot×Moment truth.
