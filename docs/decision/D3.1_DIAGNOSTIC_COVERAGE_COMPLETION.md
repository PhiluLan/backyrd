## Blocking ambiguity: personalization-neutral control

The authoritative D2 specification defines personalization as a paired causal comparison and requires at least:

1. correct user and correct user history;
2. neutralized or empty history;
3. deterministically swapped, domain-opposite history from another user;
4. optionally, a repository-native non-personalized control if it needs neither a second ranking engine nor an engine change.

That specification does **not** define which current persistent Decision states constitute “history” or how each must be neutralized. Current V13 can consume several distinct user-derived states:

- V12 personalization and its feature weights;
- Taste concepts and confidence;
- place-type profile, including global and context rows;
- contextual Taste;
- recent Decision memory;
- onboarding-derived state and other observed history that feeds those projections.

The following scientifically material choices therefore remain undefined:

- whether neutral means a new synthetic user, the same user with source events removed, or the same user with derived projections cleared;
- whether onboarding remains present;
- whether V12 is retained with neutral user state or skipped;
- whether contextual Taste and place-type profile are treatment variables or controlled context;
- whether recent memory belongs to personalization lift or only the Remix/repetition arm;
- whether the opposite-history arm swaps raw events, derived state, or both;
- how to keep authentication, candidate retrieval eligibility and all non-personalized conditions identical without changing V13.

These choices can change the measured treatment itself. Choosing one in D3.1 would create a new quality/control definition after the freeze rather than merely making an existing definition executable. Using the unauthenticated V13 path is not a legitimate default: it skips V12 and changes candidate generation in addition to personalization. It therefore cannot isolate personalization lift.
