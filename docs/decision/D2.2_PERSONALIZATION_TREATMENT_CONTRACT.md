# D2.2 Personalization Treatment Contract

## Executive summary

D2.2 closes the measurement-definition gap that stopped D3.1. It defines three authenticated synthetic twins of the same latent user—`ACTUAL`, `NEUTRAL`, and `OPPOSING`—and changes only their observed personal history. Query, current Context, World, Spot universe, Ground Truth, Engine source, Product Eligibility, Distribution and Semantic retrieval remain controlled.

The treatment does not create an alternate ranking path. D3.1 must materialize the declared observed histories through the existing Product/Learning contracts and canonical database triggers, then invoke the same authenticated V13 pipeline for all arms. V12 candidate differences are valid treatment effects and must be recorded rather than suppressed.

The existing D2.1/v1.1 freeze remains intact. D2.2 adds a child scientific identity for Personalization Treatment only.

## Original specification gap

D2 required correct, neutral/empty, and opposing-history comparisons but did not define which persistent states constituted history. Current public Decision can read multiple projections with different windows and learning paths. An authenticated-versus-anonymous comparison would also disable V12 and therefore confound authentication, candidate generation and personalization.

D2.2 resolves this by defining the treatment at the observed-history boundary. It does not zero weights or edit projections. Each arm is a distinct authenticated synthetic account that represents the same evaluation-only latent person.

## ACTUAL contract

`ACTUAL` is an authenticated twin whose observed history is a deterministic replay of the source synthetic user's observed interactions. Informative Product actions use the same multi-path calls used by Mobile:

- `backyrd_ml_log_event_v1` for ML features, contextual Taste, place type and memory;
- `backyrd_log_taste_event_v3` for legacy concept Taste;
- Decision action logging where a source action has an equivalent canonical Decision contract;
- `complete_decision_onboarding_v1` only when at least three explicit observed onboarding Spot IDs exist.

Event occurrence time is preserved. This is necessary because V12 behavior uses 3/21/45-day windows and V13 memory uses 48 hours.

## NEUTRAL contract

`NEUTRAL` is a new authenticated synthetic twin with the same non-treatment account/profile/current-scenario controls, but:

- no preference-bearing onboarding selections;
- no informative Product, Decision, Taste or ML history;
- consequently no feature-weight, concept, contextual-Taste or place-type projections;
- no recent memory.

This is a canonical reachable state: a registered authenticated user before preference-bearing activity. It is not an anonymous path and no existing state is deleted or manually zeroed.

Cold Start may yield `ACTUAL ≈ NEUTRAL`; that is a valid measurement outcome, not an acceptance expectation.

## OPPOSING contract

`OPPOSING` is an authenticated twin with controlled observed history. The isolated generator uses the source user's latent preference only to choose **which observed, eligible Spots** represent low-affinity versus high-affinity dimensions. The resulting Engine plan contains only Spot IDs, event types, ranks, timestamps and ordinary Product context; latent values and direction labels never enter Product tables or V13 input.

The generator:

1. deterministically selects approved, Distribution-eligible Spots whose observed category/mood features align with low-affinity dimensions;
2. creates positive history for those Spots;
3. creates limited negative history for observed high-affinity dimensions;
4. scales only event count by the frozen maturity cohort;
5. materializes all projections through canonical calls/triggers.

It does not inject random bad rankings, scores or feature weights. For true Cold Start the opposing history is empty by contract; D3.1 must not manufacture maturity that the cohort does not possess.

## Raw events versus derived state

Raw observed history is authoritative. Derived tables must be produced by the canonical Learning pipeline. Direct INSERT/UPDATE into feature weights, Taste concepts, contextual Taste or place-type profiles is prohibited.

D3.1 may use isolated event-table insertion only as a behavior-neutral historical-clock adapter when a production RPC always uses `now()`. Such insertion must use the exact canonical event schema and leave the canonical triggers enabled. It may not write a projection directly. After materialization D3.1 must assert raw/derived consistency and snapshot the rows consumed by V12/V13.

## Memory treatment

Recent Memory is included in the total observed-history treatment because it arises from the same history and removing it separately would add another intervention. It must also be reported independently:

- `ACTUAL MEMORY`: natural events inside the 48-hour window;
- `NEUTRAL MEMORY`: empty because Neutral has no history;
- `OPPOSING MEMORY`: only opposing events naturally inside the window.

The current frozen generator intentionally places controlled opposing history outside 48 hours, so its primary opposing treatment isolates durable learning. Actual Memory may remain non-empty and is part of the total real-world history effect. D3.1 must report both total lift and a memory-contribution decomposition; the separate Remix/Memory arm remains responsible for causal memory-only analysis.

## Onboarding treatment

Preference-bearing Decision onboarding is personal history:

- Actual replays explicit observed onboarding choices only;
- Neutral does not complete preference onboarding;
- Opposing uses three deterministic opposing observed Spots;
- profile authentication/city remain identical in all arms.

If Actual lacks three explicit onboarding selections, onboarding preference state is absent in all arms. A completion boolean or unrelated later positive activity is insufficient evidence. D1 currently stores only the completion boolean, so the v1 fixtures do not activate this component. This avoids contaminating Actual with reconstructed preferences and ensures Opposing changes the same declared treatment support rather than adding an extra data source.

## Candidate generation implications

All arms call the same authenticated V13 handler. V12 remains active. The treatment is allowed to change:

- V12 candidates and ranks;
- Semantic/V12 overlap membership;
- union composition;
- V13 fusion contributions and final ranks.

Semantic retrieval itself should be stable because query, embedding mode, document universe and exclusions are controlled. D3.1 must record unexpected semantic-set differences as a control failure. It must never force identical V12 or union candidates.

## Scientific control invariants

The adversarial validator enforces twelve controls:

1. Identity: three authenticated twin IDs, one latent-truth reference.
2. Context: identical current query and Context.
3. World: identical World/seed/Spot-universe hash.
4. Engine: identical V13 hash and Semantic path.
5. Neutrality: no directed history/onboarding in Neutral.
6. Opposing direction: deterministic opposing observed history.
7. Internal consistency: canonical learning only; no direct projection writes.
8. No latent leakage into Engine plans.
9. Same-seed treatment hash reproducibility.
10. Candidate attribution readiness across retrieval and ranking.
11. Anonymous path prohibited.
12. Engine weight/score overrides prohibited.

Ground Truth is evaluated with the original source user's latent truth for all three twins.

## Metrics contract

D3.1/D3 may compute, without changing thresholds:

- `Personalization Lift = Utility(ACTUAL) − Utility(NEUTRAL)`;
- `Personalization Harm = share[Utility(ACTUAL) < Utility(NEUTRAL)]`;
- `Opposing History Impact = Utility(OPPOSING) − Utility(ACTUAL)`;
- Current Intent Robustness using the frozen intent/context utility relation;
- paired Recall, NDCG, Top-K Utility and regret deltas;
- Candidate/Jaccard differences and rank movement;
- V12, Semantic, overlap and final-source contribution deltas;
- Taste, contextual Taste, place-type and recent-memory contribution deltas;
- paired bootstrap interval and Win/Tie/Loss per D2.

No new V13 quality threshold is introduced.

## D3.1 integration contract

D3.1 may now:

1. create the three authenticated twin accounts in a disposable synthetic database;
2. materialize each `enginePlan` with canonical calls/triggers and preserved historical time;
3. assert projection consistency and zero latent fields;
4. call the same canonical V13 snapshot for all arms;
5. evaluate all arms against the same source latent truth;
6. measure retrieval and ranking effects separately;
7. add Counterfactual, Remix and Explanation arms without reinterpreting this treatment.

D3.1 must fail closed on treatment/freeze hash mismatch, unauthenticated control, direct projection writes, current-request drift, World drift, Engine drift or missing arm coverage.

## Remaining limitations

- The generator specifies executable canonical calls but D2.2 does not run V13 or report V13 quality.
- Historical-clock materialization requires a D3.1 adapter because `backyrd_ml_log_event_v1` uses `now()`; triggers must remain canonical.
- Actual source events in D1 are noisy observations and may be sparse. D3 must report exposure, not assume lift.
- D1 does not retain onboarding selection IDs; onboarding preference treatment remains inactive until an observed selection payload exists.
- Opposing direction selection occurs in the isolated generator and is valid only if its emitted Engine plan remains latent-free.
- Memory-total and memory-only effects must not be conflated.
