# World Knowledge Week 1 — Production release foundation

Status: **CTO review only**. `executionAuthorized` is `false`. This runbook must not be used to touch Production until a separate, exact-SHA release authorization exists.

## Bound release unit

The executable contract is generated by:

```sh
node scripts/world-knowledge/build-week1-production-release-foundation.mjs
```

It derives pending work from `delivery/production-state.json` to the exact candidate and fails closed unless the result is exactly the nine immutable World Knowledge migrations. It also rejects Edge Function or Auth deployment scope. The migration bundle hash binds order, paths and file SHA-256 values.

## Ordered procedure

1. **Preflight**
   - Resolve canonical Main and require the approved candidate SHA and tree.
   - Rebuild the source-aware plan and compare plan and bundle hashes.
   - Require the attested Production migration tip and schema/ACL fingerprints.
   - Run the remote migration dry-run read-only only after separate authorization.
   - Stop for any unexpected migration, function, Auth change, hash difference or schema drift.
2. **Backup**
   - Require a current physical backup and a separate logical schema/data dump.
   - Record backup identity, completion time, encryption and restore target.
   - Perform a restore rehearsal into an isolated project before Apply is authorized.
3. **Rehearsal**
   - Start a disposable local stack with a unique project ID and ports.
   - Restore a sanitized, production-shaped synthetic dataset; never copy private Production rows.
   - Apply the nine files in bound order with per-file timing and `ON_ERROR_STOP`.
   - Run the full SQL authorization suite, inventory RLS/grants/functions, and compare schema/ACL fingerprints.
   - Repeat the safe replay checks; append-only ledgers and registry releases must not duplicate or mutate.
4. **Apply — blocked in Week 1**
   - Requires a new CTO release authorization naming exact candidate SHA, tree, plan hash, migration bundle hash and backup evidence.
   - Use the protected source-aware workflow only. Never run migrations manually from a laptop.
5. **Verify**
   - Confirm migration ledger order and byte hashes.
   - Compare application schema and public ACL fingerprints.
   - Verify all private World tables deny `PUBLIC`, `anon` and `authenticated` direct access.
   - Verify only intended RPCs have minimal execution grants and every `SECURITY DEFINER` function has `search_path=''` and fully qualified relations.
   - Confirm no World runtime, Decision wiring, ranking or client surface became active.
6. **Rollback / forward recovery**
   - Before any Product activation, prefer restoring the verified backup if Apply fails.
   - Never edit the migration ledger, delete append-only claims, or rewrite a published migration.
   - If data was accepted after Apply, stop all World writes and design an explicit forward recovery; do not destructively down-migrate.

## Stop conditions

- Production differs from the attested shipped baseline.
- Backup or restore proof is absent.
- Any path, byte hash, plan hash, project reference or migration order differs.
- Lock duration or total runtime exceeds the approved budget.
- An unexpected table rewrite, destructive DDL, data backfill or external call appears.
- RLS, grants, function execution or private-schema exposure differs from the accepted inventory.
- Missing, `UNKNOWN`, `NOT_CONFIGURED` or `DISPUTED` data is collapsed into `false` or authorized truth.
- Any Decision, User Intelligence, Edge Function, Auth, deployment or Product activation enters scope.

## Cohort boundary

The Week-1 cohort tool may suggest 20–40 diverse Basel spots and report field coverage. Suggestions are not Claims. It may not create `OWNER_CONFIRMED`, `ADMIN_CONFIRMED` or `VERIFIED` evidence. Missing fields remain absent, and `UNKNOWN`, `NOT_CONFIGURED` and `DISPUTED` remain distinct. Decision consumes only a later sanitized, approved read-only handoff.
